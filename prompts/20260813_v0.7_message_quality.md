# v0.7 开发信与客户回复质量优化

## 范围

在不改变 v0.6 单客户持续跟进、localStorage key、任务主体结构和现有四项核心功能的前提下，小范围提高客户分类、LinkedIn 连接邀请、首次开发信、AI 优化和后续回复的可直接使用质量。不接入数据库、登录、新模型、抓取、群发、自动发送或部署能力。

## 实施边界

1. 客户分类统一为 Distributor / Dealer、Agent、End User / Factory、System Integrator / Engineering Company、Service / Maintenance Provider、Trader、Manufacturer / Competitor、Industry Contact、Unknown 九类；不得只凭职位、国家或单个关键词判断。
2. 视觉结构化结果增加向后兼容的 `confirmedFacts`、`reasonableInferences`、`unknownInformation`，缺失时读取为空数组。
3. 人工确认字段标记为 `user_confirmed`，可作为当前客户事实使用；推测和未知内容仍不能进入确定性陈述。
4. LinkedIn 邀请不超过 300 个英文字符，只保留一个沟通目的；首次开发信默认 80–160 个英文单词、一个易答问题和一个相关能力方向。
5. 不同客户类型使用不同沟通策略；同行和行业联系人改为非敏感行业交流，Unknown 先确认身份或需求。
6. AI 优化保留消息 ID/顺序，并在返回后执行长度、问题数和禁止承诺检查。
7. 后续回复优先回应最新客户消息，只读取当前 task 最近 20 条已记录沟通，不把未发送草稿当作历史事实；敏感问题缺少事实时必须返回缺失信息、风险和安全过渡回复。
8. 代表性测试使用合成客户资料，覆盖客户类型、价格、认证、独家、暂无需求、避免重复提问、任务隔离和异常结构化输出。

## 兼容性

继续使用 `trade-assistant.tasks.v1`。旧任务不要求重新生成；新增分析数组缺失时由 repository 补空数组。保留旧的“设备集成商”“工程项目方”“其他”等联合类型以便读取历史数据，新生成和人工选择使用统一的新标签。

## 真实视觉模型结构化输出修复

人工验收发现视觉模型的常见格式波动会被统一映射成 `MODEL_OUTPUT_INVALID`，且旧诊断没有保留 JSON 提取阶段或 Schema 路径。修复限定在现有视觉分析链路：

1. 安全提取响应中的第一个完整 JSON 对象，支持 Markdown JSON 代码块和 JSON 前后少量说明，不执行代码或宽松表达式求值。
2. 对非关键字符串数组执行有限归一化：缺失/null 变为空数组，单字符串变为单项数组，非法对象被丢弃且不能成为事实。
3. customerType 支持大小写、中文常用称呼和旧 `oem_integrator`，无法安全映射时保持 Unknown。
4. 非关键 outreach、inferences 和推荐数组波动使用安全默认值；若姓名、职位、公司、行业和公司业务全部不可用，则以 `MODEL_CORE_DATA_MISSING` 安全失败。
5. 区分空响应、JSON 解析失败、Schema 失败和核心数据缺失。开发环境日志只记录代码块/额外文字标志、顶层字段类型和 Schema path，不记录字段值、模型正文、截图或 API Key。
## 真实视觉回归修复：职责拆分

- 视觉阶段只提取截图直接可见的基础客户资料，不再要求九类客户分类、事实/推断分组、沟通策略或开发信。
- `customerType`、事实边界、客户类型策略、连接邀请、首次开发信及防过度承诺规则继续由后续客户分析与文案生成阶段处理。
- 视觉响应沿用原有结构化字段格式；缺失的非核心 v0.7 字段由解析层提供安全默认值，旧版 v0.6 完整响应仍可读取。
- 开发环境的解析诊断只记录响应长度、代码块/附带文字标记、JSON 错误类别和位置、顶层字段类型及 Schema 路径，不记录正文或字段值。
